# Ace Place — использование и администрирование

Telegram-бот для бронирования одной площадки party room целиком. Клиенты оформляют заявки в личном чате, администраторы проверяют оплату и подтверждают аренду. Интерфейс доступен на русском и корейском языках.

**Стек:** Python 3.12.10, PostgreSQL 18, python-telegram-bot, Docker Compose. Google Calendar отображает подтверждённые брони, блокировки и уборки. FastAPI предоставляет проверки работоспособности; для работы бота запускать его необязательно. LLM и Mini App не подключены.

**Источник данных — PostgreSQL.** Кнопки календаря в чате выбирают дату, а Google Calendar служит отдельным представлением расписания.

Пошаговый перенос на Ubuntu VPS, включая Docker, рабочие настройки и текущую БД: [инструкция по развёртыванию](DEPLOYMENT.md).

## Быстрый запуск существующего проекта

Все команды выполняются в PowerShell из корня проекта. Запустите Docker Desktop и дождитесь готовности Linux Engine. Для существующей настроенной БД повторно применять миграции не нужно.

```powershell
docker compose --profile bot up -d --build bot
docker compose ps
docker compose logs --tail 50 -f bot
```

Compose запускает PostgreSQL, ждёт его готовности и запускает бота. Ctrl+C при просмотре логов прекращает только просмотр — контейнер продолжает работать.

Откройте личный чат с ботом и отправьте `/start`; для административного меню — `/admin`.

**Один Telegram-токен — один процесс polling.** Перед запуском контейнера остановите локальный `python -m app.bot`. При остановке компьютера или переходе в сон локальный бот недоступен.

Альтернативный запуск для разработки на Windows:

```powershell
docker compose stop bot
docker compose up -d --wait db
.\.venv\Scripts\python.exe -m app.check_db
.\.venv\Scripts\python.exe -m app.bot
```

Остановка локального бота — Ctrl+C в его терминале.

## Инструкция для клиента

### Команды

| Команда | Действие |
| --- | --- |
| `/start`, `/help` | Открыть главное меню |
| `/language` | Открыть меню с выбором русского или корейского языка |
| `/book` | Начать оформление заявки |
| `/get_user_id`, `/myid` | Узнать свой числовой Telegram ID |
| `/cancel` | Прервать текущий ввод; существующая бронь не отменяется |
| `/admin` | Открыть административное меню при наличии прав |

При первом обращении клиент регистрируется автоматически. Username не является идентификатором: он может измениться. Выбранный язык сохраняется в БД.

Возле поля ввода доступна стандартная кнопка Telegram **«Меню»**: `/start`, `/book`, `/help`, `/get_user_id`, `/language`, `/cancel`. Владельцу и активному администратору дополнительно показывается `/admin`. Команды можно вызвать в любой момент, независимо от старых сообщений; `/cancel` завершает только текущую форму. `/get_user_id` и прежняя `/myid` возвращают один и тот же ID.

Меню настраивается ботом автоматически, без BotFather. Подписи соответствуют выбранному в боте языку. При смене языка и изменении прав через интерфейс меню обновляется сразу; после bootstrap или внешних изменений БД — при следующем обращении либо фоновой сверке примерно раз в минуту. Telegram-клиент может отобразить обновление после повторного открытия чата. Сбой обновления меню не отменяет выполненную операцию; права на команды всегда проверяются отдельно на сервере.

### Создание заявки

1. Нажмите **«Забронировать»** или отправьте `/book`.
2. Выберите дату в календаре. Стрелки переключают месяцы; прошедшие дни помечены `×` и недоступны. Можно ввести дату как `YYYY-MM-DD`.
3. Выберите длительность кнопкой или введите целое число часов. Минимум — 5 часов.
4. Выберите доступное время начала. Часы указаны по Сеулу (`Asia/Seoul`).
5. Ответьте на три вопроса: телефон для связи (кнопкой «Поделиться контактом» или вручную), количество гостей и мероприятие.
6. Проверьте даты, ответы, стоимость, реквизиты и условия отмены. Кнопка **«Изменить ответы»** позволяет заново заполнить анкету, сохранив выбранное время.
7. Нажмите **«Отправить заявку»**. До этого действия время не резервируется.
8. Переведите предоплату по реквизитам, указанным ботом.
9. В карточке заявки нажмите **«Отправить подтверждение оплаты»** и отправьте один скриншот.
10. Дождитесь проверки банка и подтверждения брони администратором.

Телефон сохраняется для конкретной брони; допускается международный формат с `+`. Количество гостей вводится целым положительным числом. Технический предел 10000 не является правилом вместимости помещения. Название/тип мероприятия — до 200 символов. Ответы отображаются в карточках клиента и администратора, Telegram-уведомлениях администраторам и описании события аренды в Google Calendar после подтверждения. Остаток к оплате в календаре учитывает все полученные платежи. У старых и ручных броней анкета может отсутствовать.

Скриншот принимается как фото либо файл PNG/JPEG/WebP размером до 10 МБ. Изображение привязывается к выбранной брони. Его отправка сама по себе не подтверждает ни оплату, ни аренду.

Одновременно разрешена одна ожидающая заявка клиента. При сохранении бот заново проверяет доступность и стоимость: выбранное время мог занять другой клиент.

### Просмотр и отмена

В разделе **«Мои брони»** доступны только собственные записи. Отменённые записи скрыты в списке, но сохраняются в БД. **«Обновить статус»** показывает актуальную карточку.

Неподтверждённую неоплаченную заявку можно отозвать кнопкой **«Отозвать заявку»**. Собственную будущую подтверждённую бронь или заявку с учтённой оплатой можно отменить кнопкой **«Отменить бронь»**. Перед отменой бот показывает условия и точный расчёт по подтверждённым платежам, затем запрашивает отдельное согласие. Перенос и отмена после начала аренды согласуются с администратором.

**Условия отмены:** за 72 часа и более до начала возвращается вся подтверждённая оплата. При отмене менее чем за 72 часа удерживается только фактически полученная предоплата, максимум 50 000 KRW по текущим условиям. Учтённый остаток оплаты подлежит возврату. Например, при полученных 50 000 KRW предоплаты и 100 000 KRW остатка поздняя отмена означает возврат 100 000 KRW. Ровно 72 часа относятся к полному возврату; используются часы, а не календарные даты.

Условия видны до отправки заявки и в карточке брони, включая подтверждение от администратора. Они сохраняются в новых бронях как снимок: изменение конфига не меняет согласованные условия. Для старых записей без снимка используются текущие условия, показанные перед отменой. Если расчёт изменился между открытием подтверждения и нажатием кнопки, требуется новое согласие. При отмене клиент и администраторы получают уведомления с удержанием, суммой и состоянием ручного возврата. Не проверенные по скриншоту переводы в расчёт не входят и требуют сверки с администратором.

После подтверждения клиент получает адрес, маршрут, если задана ссылка, и инструкцию входа на своём языке. При переносе, отмене или истечении срока приходит соответствующее уведомление.

### Отзыв после посещения

При `reviews.enabled: true` бот назначает клиенту одно приглашение оставить отзыв после окончания аренды (`ends_at`), не дожидаясь уборки. Фоновый цикл проверяет отправки каждые 30 секунд, поэтому сообщение обычно приходит в течение 30 секунд после окончания при работающем боте и доступном Telegram.

Настройки в `config.yaml`:

```yaml
reviews:
  enabled: true
  url: "https://t.me/AcePlaceParty/112"
  catch_up_hours: 24
  ru:
    link_text: "⭐ Оставить отзыв"
    message: |-
      Спасибо, что выбрали AcePlace! 🎉
      Надеемся, вы отлично провели время.

      Поделитесь впечатлениями — ваш отзыв поможет нам стать лучше и другим гостям выбрать место для своего мероприятия.

      {review_link}

      Будем рады видеть вас снова! 💛
```

Аналогичный блок `reviews.ko` содержит корейский текст и подпись; полный пример обоих языков находится в `config_example.yaml`. Сообщение пишется обычным текстом, а `{review_link}` должно встречаться ровно один раз. Бот заменяет его жирной кликабельной ссылкой из `url` и `link_text`. HTML/Markdown в остальном тексте не интерпретируется; предпросмотр ссылки отключён. В шаблоне конфигурации отправка выключена, в рабочем локальном конфиге включена. На VPS добавьте или включите этот раздел и перезапустите бота.

Приглашения заранее назначаются подтверждённым арендам с Telegram-клиентом и будущим временем окончания. Перенос меняет время ожидающего приглашения; отмена отключает его. Блокировкам и арендам без клиента сообщение не назначается. Состояние хранится в существующем `bookings.admin_notifications`; новая миграция для отзывов не нужна. Успешная отправка не повторяется после перезапуска. При потере ответа Telegram после фактической доставки возможен повтор в рамках общей механики повторных попыток.

Если ранее назначенная отправка пропущена из-за остановки бота, она выполняется после запуска только в пределах `catch_up_hours` после окончания (целое число от 1 до 168). Впервые уже завершённым броням сообщения не назначаются — включение функции не запускает массовую рассылку по старым посещениям. При изменении оплаты ожидающее приглашение сохраняется; отмена повторно проверяется перед отправкой. Момент изменения статуса одновременно с уже начатым сетевым запросом полностью исключить нельзя.

### Поведение сообщений

Меню, списки, календарь и карточки просмотра используют один временный экран. Пройденные подсказки и исправленные ошибки убираются. Сообщения пользователя, результаты действий, реквизиты, скриншоты и отдельные уведомления сохраняются.

После перезапуска старые сообщения не очищаются массово. Если кнопка устарела, откройте `/start`, `/book` или `/admin` заново. Видимость кнопки не заменяет серверную проверку прав и статуса записи.

## Инструкция для администратора

### Меню `/admin`

| Кнопка | Назначение |
| --- | --- |
| **Все брони** | Просмотр записей и блокировок, кроме отменённых; по 8 на страницу |
| **Ожидают решения** | Заявки со статусом `pending` |
| **Создать заявку** | Создание аренды от имени администратора |
| **Блокировать время** | Закрытие интервала без клиента, оплаты и уборки |
| **Блокировки** | Поиск сохранённых блокировок и снятие ограничения |
| **Ожидают возврата** | Отменённые клиентом брони с положительной суммой ручного возврата |
| **Администраторы** | Управление сотрудниками; доступно только владельцу |

### Проверка оплаты и подтверждение

1. Откройте ожидающую заявку или уведомление о скриншоте.
2. При необходимости нажмите **«Посмотреть скриншот»**.
3. Проверьте фактическое поступление денег в банковском приложении.
4. Нажмите **«Предоплата получена»** и подтвердите действие. Бот записывает сумму ожидаемой предоплаты; бронь пока остаётся неподтверждённой.
5. Отдельно нажмите **«Подтвердить»** в карточке брони и подтвердите действие.

Если доказательство оплаты не подходит, выберите **«Запросить другой скриншот»**. Клиент сможет отправить замену; суммы оплаты не изменяются.

Скриншот можно получить и после истечения/отмены заявки. В этом случае требуется ручное решение администратора: автоматическое восстановление времени и приём предоплаты через обычную кнопку запрещены.

**Проверка предоплаты и подтверждение брони — два отдельных действия.** Скриншот или запись предоплаты не останавливают срок ожидания неподтверждённой заявки.

### Создание заявки вручную

1. Нажмите **«Создать заявку»**.
2. Выберите дату и час начала, затем дату и час окончания. Альтернатива — ввод `YYYY-MM-DD HH:MM`.
3. Для окончания после полуночи выберите следующую дату. Для аренды минимум составляет 5 часов.
4. Введите Telegram ID зарегистрированного клиента либо `-`, если клиент не пользуется ботом.
5. Введите `авто` / `auto` для тарифа из конфига либо согласованную полную стоимость, например `150000 KRW`.
6. Проверьте итоговую карточку и нажмите **«Да, выполнить»**.

Новая заявка получает `pending` и требует отдельного подтверждения. Административный выбор часов не гарантирует свободный интервал: занятость окончательно проверяется при сохранении.

### Перенос и отмена

Откройте запись через список, выберите **«Перенести»** или **«Отменить запись»**, затем подтвердите действие.

При переносе задаются новые начало и окончание, пересчитывается уборка. Согласованная стоимость сохраняется. Если новый интервал занят, исходная бронь остаётся на месте.

Клиент получает уведомление; другие активные владельцы/администраторы с включёнными уведомлениями также получают информацию об изменении. Администратору, выполнившему действие, отдельное уведомление об этом действии не дублируется.

### Возврат после отмены клиентом

Откройте **«Ожидают возврата»**, проверьте расчёт и выполните банковский перевод клиенту вручную. Только после фактического перевода нажмите **«Возврат выполнен»** и подтвердите действие. Клиент получит уведомление. Бот не отправляет деньги автоматически и не обнуляет ранее полученные суммы; состояние возврата хранится отдельно в записи брони. Если возврат равен нулю, задача ручного возврата не создаётся. Обычные списки по-прежнему скрывают отменённые записи.

Самостоятельная отмена клиентом рассчитывает возврат по сохранённым условиям. При административной отмене через прежнюю кнопку или поздней/неучтённой оплате финансовое решение остаётся ручным: автоматическая задача возврата для таких случаев не формируется.

### Блокировка времени

Через **«Блокировать время»** выберите начало и окончание и нажмите **«Да, выполнить»**. Только после подтверждения блокировка сохраняется и отправляется в календарь.

Чтобы снять её после любых других действий: **`/admin` → «Блокировки» → нужная запись → «Снять блокировку» → подтверждение**.

Блокировка имеет нулевую стоимость, не привязана к клиенту и не создаёт уборку. После снятия она исчезает из списков, освобождает время и удаляется из Google Calendar при синхронизации.

## Владелец и управление доступом

### Первое назначение владельца

Будущий владелец должен отправить боту `/start`, затем `/myid`. В доверенном локальном терминале выполните команду со своим Telegram ID:

```powershell
.\.venv\Scripts\python.exe -m app.bootstrap_owner --telegram-id 123456789
```

Если используется только Docker:

```powershell
docker compose --profile bot run --rm --no-deps bot python -m app.bootstrap_owner --telegram-id 123456789
```

Необязательный `--google-email "owner@example.com"` сохраняет адрес в БД и не выдаёт доступ к Google Calendar.

Bootstrap предназначен только для первого владельца. Повтор для того же владельца ничего не меняет, включая отключённый доступ; назначить другого владельца этой командой нельзя.

### Роли

| Роль | Возможности |
| --- | --- |
| Клиент | Собственные брони, отправка скриншота, отзыв неподтверждённой заявки |
| `operator` | Просмотр своей роли; управление расписанием пока недоступно |
| `admin` | Управление бронированиями, блокировками и ручной проверкой предоплаты |
| `owner` | Все возможности `admin` и управление сотрудниками |

`operator` пока не входит в получателей административных уведомлений, даже при включённом флаге. Административные функции доступны в личном чате с ботом.

### Добавление и отключение сотрудников

1. Будущий сотрудник отправляет этому боту `/start` и сообщает владельцу свой `/myid`.
2. Владелец открывает **`/admin` → «Администраторы» → «Добавить администратора»**.
3. Вводит числовой Telegram ID, выбирает `admin` или `operator` и подтверждает действие.
4. В карточке сотрудника может менять роль, уведомления, отключать или восстанавливать доступ.

Отключённые сотрудники остаются в списке. Их пользователи и брони не удаляются. Если сотрудник уже существует, открывается его карточка; повторное добавление не включает доступ автоматически.

Назначение роли `owner`, изменение роли владельца и отключение владельца через Telegram запрещены. Владелец может отключить собственные уведомления. Права проверяются при каждом действии, включая финальное подтверждение; устаревшая форма не перезаписывает новые права.

## Правила бронирования

Все пользовательские даты и недельное расписание трактуются по `Asia/Seoul`. В БД используются `timestamptz`, соединения приложения работают в UTC. Минимальная аренда — 5 часов; начала и длительности — целочасовые.

Текущие тарифы из `config.yaml`:

| Тариф | Первые 5 часов | Каждый дополнительный час |
| --- | ---: | ---: |
| Будни | 150 000 KRW | 10 000 KRW |
| Выходные и праздники | 200 000 KRW | 20 000 KRW |

Вся аренда считается по дате её начала в Сеуле, включая часы после полуночи. `amount` — полная стоимость. `deposit_paid_amount` и `balance_paid_amount` — фактически записанные суммы; валюта хранится в `unit`. Предоплата — 50 000 KRW, она входит в общую стоимость.

Неподтверждённая заявка ожидает решения до 24 часов (1440 минут), но не позже начала аренды. Короткое удержание `hold` имеет срок 10 минут и используется сервисом/CLI. Работающий бот проверяет истечение каждые 30 секунд. Если бот был выключен, обработка возобновляется после запуска; уже истёкшие заявки не считаются занятыми при поиске доступности.

| Статус | Значение |
| --- | --- |
| `hold` | Временное удержание |
| `pending` | Ожидание подтверждения администратора |
| `confirmed` | Подтверждённая аренда или действующая блокировка |
| `cancelled` | Отменено; запись сохранена в БД |
| `expired` | Истёк срок ожидания |
| `completed` | Завершено; отдельной кнопки автоматического завершения сейчас нет |

### Уборка и занятость

После аренды выбирается ближайший разрешённый старт уборки из `cleaning.weekly`. Длительность задаётся отдельно в `cleaning.duration_minutes`; сейчас это 120 минут. До окончания уборки площадка занята, включая ожидание разрешённого старта.

Например, аренда заканчивается в 22:00:

- если разрешён старт в 22:00, уборка займёт 22:00–00:00; новая аренда возможна с 00:00;
- если ближайший разрешённый старт — завтра в 09:00, площадка занята до завтра 11:00.

Выбранный слот сохраняется в брони. Редактирование недельного конфига само по себе не пересчитывает существующие брони. Явный перенос пересчитывает уборку. PostgreSQL запрещает пересечение занятых интервалов действующих записей; при совпадении границ следующая аренда может начинаться ровно после уборки.

| Раздел | Что настраивается |

После изменения конфига перезапустите бота. В Docker файл подключён только для чтения; редактируйте его на хосте.

Напоминание об уборке сейчас настроено за 1 час:

```yaml
notifications:
  cleaning:
    hours_before: 1
    telegram_enabled: true
```

`hours_before` — целое число от 1 до 168. Напоминание получают активные `owner`/`admin` с включёнными персональными уведомлениями. После перезапуска пропущенное напоминание отправляется, только если уборка ещё не началась. Перенос и отмена учитываются при подготовке и отправке напоминаний.

В `visit` заполните `address`, `route_url`, `entry_instructions` для каждого языка. Эти данные добавляются к подтверждению клиенту. Пустые поля пропускаются; отсутствующий перевод берётся из другого языка. Заполнение конфига не рассылает инструкции заново по старым подтверждениям. В текущем конфиге адрес и парковка заполнены, ссылка `route_url` пока пустая.

Разрешённые старты уборки задаются для всех семи дней:

```yaml
cleaning:
  policy: next_start_time
  duration_minutes: 120
  weekly:
    MON: ["09:00", "14:00", "23:00"]
    TUE: []
    WED: ["09:00", "14:00"]
    THU: ["09:00", "14:00"]
    FRI: ["09:00", "14:00"]
    SAT: ["09:00", "14:00"]
    SUN: ["09:00", "14:00"]
```

Это пример расписания. В рабочем `config.yaml` сохранены разрешённые старты каждый час всех дней. Время указывается в кавычках как `HH:MM`, в часовом поясе Сеула; допустимы и значения вроде `10:30`. `[]` означает отсутствие стартов в этот день; `null` — неизвестное расписание, при котором расчёт может быть отклонён. `duration_minutes` — целое число от 1 до 1440. При старте в 23:00 и длительности 120 минут уборка закончится завтра в 01:00.

Старый формат `from`/`to` поддерживается как диапазон разрешённых часовых стартов: `from` включается, `to` исключается. Например, 09:00–10:00 допускает старт в 09:00, а уборка длительностью 120 минут завершится в 11:00. Ночной диапазон относится к дню начала. Новые настройки применяются при создании и переносе; сохранённые интервалы существующих броней не меняются. Перед запуском нового кода на существующей БД примените `011_cleaning_duration`.

Праздники Южной Кореи рассчитываются автоматически библиотекой `holidays` (календарь `KR`, публичные праздники, включая переносы). Расчёт выполняется локально, без HTTP-запросов и API-ключей; рассчитанные годы кешируются в памяти. [Поддержка Южной Кореи в holidays](https://holidays.readthedocs.io/en/latest/auto_gen_docs/south_korea/).

`pricing.holiday_dates` — дополнительные даты праздничного тарифа, которые вы задаёте вручную. При расчёте они объединяются с календарём библиотеки; файл YAML автоматически не перезаписывается. Обычные праздники дублировать не нужно, но дубликаты не меняют стоимость. Прежний список рабочего конфига сохранён.

```yaml
pricing:
  # Остальные тарифные параметры остаются здесь же.
  holiday_dates:
    - "2027-11-04" # Пример своей даты повышенного тарифа
```

Пустой список `holiday_dates: []` включает только автоматические праздники и настроенные выходные. Тариф всей аренды и дополнительных часов определяется по дате начала в Сеуле. Редактирование ручных дат учитывается при следующем расчёте без перезапуска; уже согласованные суммы существующих броней не пересчитываются.

`verified_holiday_years` больше не требуется; старое поле принимается для совместимости и не ограничивает расчёт. Установленная версия библиотеки поддерживает 1948–2100 годы. Если календарь для буднего дня рассчитать нельзя, бот сообщает об ошибке вместо назначения буднего тарифа. Библиотека не загружает новые решения о разовых праздниках из интернета: такие даты можно добавить вручную сразу, а правила библиотеки обновляются вместе с зависимостями и новым Docker-образом.

### Регулярные блокировки (`books_plans`)

В `config.yaml` раздел `books_plans` задаёт регулярную занятость любого назначения. Каждый день `weekly` содержит список диапазонов `from`/`to`: можно указать несколько диапазонов за день. Время задаётся в кавычках, в часовом поясе Сеула. Ночной диапазон относится к дню начала, например пятница 23:00–01:00 заканчивается в субботу. Диапазоны не должны пересекаться, в том числе через границу недели; соприкасающиеся границы допустимы.

Сейчас раздел выключен (`enabled: false`), все дни пустые (`[]`), пример двух диапазонов оставлен комментариями. Для включения задайте `enabled: true` и замените нужный пустой день списком:

```yaml
MON:
  - from: "10:00"
    to: "12:00"
  - from: "14:00"
    to: "16:00"
```

При работающем боте изменения применяются автоматически в очередном цикле (обычно в течение 30 секунд). В БД создаются блокировки на `generate_days_ahead` дней (по умолчанию 90; допустимо 1–366); горизонт ежедневно продлевается. Поиск свободного времени и создание/перенос брони проверяют расписание сразу, включая даты за этим горизонтом и уборку после аренды. Регулярная блокировка сама уборки не требует. Это работает и при выключенном или недоступном Google Calendar.

В Google Calendar каждый недельный диапазон отображается отдельным **повторяющимся событием**, а не набором одиночных событий. Серия имеет ограничение до конца подготовленного горизонта, которое бот продлевает. Используются RRULE и исключения EXDATE; часовой пояс — `Asia/Seoul`. [Документация Google о повторяющихся событиях](https://developers.google.com/workspace/calendar/api/guides/recurringevents).

- Удаление диапазона или `enabled: false` отменяет его будущие блокировки в БД и обрезает будущую часть серии Google. Прошедшие и начавшиеся занятия сохраняются.
- Изменение часов завершает старую серию и создаёт новую. Повторное включение также создаёт новую серию, чтобы не восстанавливать отменённые события в прошлом.
- `excluded_dates` исключает все регулярные блокировки, начинающиеся в указанную дату. Изменение исключений действует на будущие занятия; начавшиеся сохраняются.
- Если новое расписание пересекает активную бронь, её уборку или ручную блокировку, существующая запись сохраняется. На конфликтующую дату блокировка не создаётся, а экземпляр серии Google исключается. Активные owner/admin с включёнными уведомлениями получают сообщение с датой и номерами записей. Новые брони в плановое время остаются запрещены, пока расписание не исправлено. При освобождении интервала блокировка восстанавливается автоматически.

В `/admin` → «Блокировки» видны будущие и текущие занятия с пометкой `books_plans`; прошедшие сохраняются в БД и Google Calendar, но скрыты из списка. Их редактируют через конфиг; кнопки отмены/переноса для них скрыты. Для отмены на дату добавьте её в `excluded_dates`; для изменения всего расписания измените `weekly`.

Новых таблиц и миграции для этой функции нет: используется `bookings.request_data` с источником `books_plans`. Блокировки дат — обычные записи `type=block`; состояние серии и её устойчивая очередь синхронизации хранятся в отдельной технической записи `type=block, status=completed`, которая скрыта из списков и не занимает время. Удалять эти записи напрямую из БД нельзя: это потеряет связь с сериями Google. Обычные брони и ручные блокировки не изменяются.

## Google Calendar

### Первое подключение

1. В Google Cloud выберите проект, включите Google Calendar API и настройте Google Auth Platform.
2. Создайте OAuth-клиент типа **Desktop app** и скачайте JSON. Web-клиент для этой команды не подходит.
3. Если приложение находится в Testing, добавьте Google-аккаунт авторизации в Test users раздела Audience.
4. Сохраните Desktop JSON в `secrets/calendars`.
5. Укажите `GOOGLE_CALENDAR_ID` в `.env`. ID находится в настройках нужного календаря → «Интеграция календаря».
6. Выполните авторизацию на Windows, войдя под владельцем календаря:

```powershell
.\.venv\Scripts\python.exe -m app.google_calendar auth
.\.venv\Scripts\python.exe -m app.google_calendar check
```

Если найдено несколько Desktop JSON, укажите нужный:

```powershell
.\.venv\Scripts\python.exe -m app.google_calendar auth --client-file "secrets/calendars/client_secret_example.json"
```

Авторизация создаёт `google_token.json`. OAuth-клиент и токен авторизации — разные файлы. Команда `check` проверяет чтение календаря и доступные цвета, не создавая события.

Включите `calendar.enabled: true` в `config.yaml` и перезапустите бота. Для первичной сверки существующих подтверждённых записей:

```powershell
.\.venv\Scripts\python.exe -m app.calendar_sync --reconcile
```

Или в Docker:

```powershell
docker compose --profile bot run --rm --no-deps bot python -m app.calendar_sync --reconcile
```

Последние команды меняют события Google Calendar. За вызов обрабатывается до 20 заданий; остальные продолжает работающий бот.

### Что синхронизируется

- Подтверждённая аренда создаёт два события: аренду и назначенную уборку, разными цветами.
- Ручная блокировка создаёт одно событие без уборки.
- Ожидающие заявки не публикуются.
- Перенос обновляет события, отмена удаляет их.
- Временные ошибки сохраняются для повторной попытки; ID событий сохраняются для защиты от дублей.
- В карточке администратора видны состояние Calendar и ошибка; есть кнопка повторной синхронизации.

Текущие цвета: аренда `9`, уборка `6`, блокировка `8`. Аренда и уборка должны иметь разные цвета; допустимы ID `1`–`11`.

Сверка управляемых событий выполняется примерно каждые 15 минут. Ручные правки в Google перезаписываются данными БД, удалённые события восстанавливаются. Новые сторонние события не импортируются и не закрывают доступность в боте. Брони изменяйте через Telegram.

### Доступ сотрудников к календарю

Доступ Google и роль в Telegram независимы. Поле `admins.google_email` само по себе не выдаёт разрешений, не подписывает на календарь и не отправляет письма.

В браузере владельца: Google Календарь → нужный календарь → «Настройки и общий доступ» → «Имеют доступ» → добавить Google email. Для редактирования личных событий используйте разрешение **«Изменять и просматривать данные о мероприятиях»**; управление общим доступом требуется только при необходимости делиться календарём дальше.

Получатель открывает приглашение из почты. Альтернатива на компьютере: «Другие календари» → `+` → «Подписаться на календарь» → вставить ID именно календаря Ace Place. Затем календарь доступен в мобильном приложении под тем же аккаунтом; включите его отображение в меню приложения. Делать календарь публичным для этого не требуется.

Справка: [предоставление доступа](https://support.google.com/calendar/answer/37082?hl=ru), [подписка по ID](https://knowledge.workspace.google.com/admin/calendar/create-and-share-a-group-calendar?hl=ru).

### Файлы в Docker

Compose подключает `secrets/calendars` с возможностью записи: обновление Google-токена использует атомарную замену файла. В контейнере путь явно задан как `/app/secrets/calendars/google_token.json`. При изменении расположения файлов согласуйте `config.yaml`, bind-mount и переменную в Compose. На Linux каталог токенов должен быть доступен для записи UID 10001 — пользователю контейнера.

```powershell
if (-not (Test-Path -LiteralPath .\config.yaml)) {
```

### Окружение и зависимости


Проверьте, что выбран именно Python 3.12.10: ключ `-3.12` выбирает установленный интерпретатор ветки 3.12 и не гарантирует patch-версию.

Если `.env` отсутствует, создайте его на основе `.env.example` и заполните значения. Существующий файл не заменяйте. Создайте каталог JSON, если его ещё нет:

```powershell
New-Item -ItemType Directory -Force -Path .\secrets\calendars | Out-Null
docker compose up -d --wait db
.\.venv\Scripts\python.exe -m app.check_db
```

На Windows PostgreSQL доступен по `127.0.0.1:15432`; внутри Compose — `db:5432`. Данные размещены в именованном volume `postgres_data`, смонтированном в `/var/lib/postgresql`.

### Инициализация пустой БД

Просмотр списка таблиц не меняет схему:

```powershell
.\.venv\Scripts\python.exe -m app.migrate
```

**Только для новой пустой базы:** примените все миграции по порядку. При ошибке остановитесь и выясните причину.

```powershell
$aceMigrations = @(
  '001_initial',
  '002_remove_cleaning',
  '003_schema_comments',
  '004_booking_requests',
  '005_cleaning_slots',
  '006_client_notifications',
  '007_change_notifications',
  '008_payment_receipts',
  '009_calendar_sync',
  '010_client_cancellations',
  '011_cleaning_duration',
  '012_booking_details'
)
foreach ($aceMigration in $aceMigrations) {
  .\.venv\Scripts\python.exe -m app.migrate --apply --migration $aceMigration
  if ($LASTEXITCODE -ne 0) { throw "Migration failed: $aceMigration" }
}
```

Миграции выполняются транзакционно. Полноценного журнала применённых миграций пока нет; для существующей базы применяйте только заведомо отсутствующие изменения. Большинство миграций не предназначены для повторного запуска. Bootstrap начальной схемы отказывается создавать уже существующие целевые таблицы. Старые миграции сохранены как последовательность изменений, а не как актуальное описание схемы по отдельности.

Для выполнения отдельной миграции из Docker используется та же команда Python:

```powershell
docker compose --profile bot run --rm --no-deps bot python -m app.migrate --apply --migration 012_booking_details
```

Этот пример предназначен для БД с уже применённой `011_cleaning_duration`. Если схема старее, сначала примените отсутствующие миграции по порядку. Не повторяйте уже применённые миграции. Docker не применяет их автоматически: остановите бота, соберите новый образ, примените отсутствующие изменения, затем запустите бота.

После инициализации запустите бота, зарегистрируйте первого владельца и настройте Google Calendar. Пока авторизация Google не готова, установите `calendar.enabled: false`.

## Техническое обслуживание

### Основные команды Docker

| Задача | Команда |
| --- | --- |
| Статус контейнеров | `docker compose ps` |
| Запуск БД | `docker compose up -d --wait db` |
| Запуск / обновление кода бота | `docker compose --profile bot up -d --build bot` |
| Перезапуск после изменения конфига | `docker compose restart bot` |
| Пересоздание после изменения `.env` | `docker compose --profile bot up -d --force-recreate bot` |
| Логи бота | `docker compose logs --tail 50 -f bot` |
| Остановка бота, БД продолжает работать | `docker compose stop bot` |
| Остановка бота и БД | `docker compose --profile bot stop` |

Для обычной остановки используйте `stop`. `docker compose down -v` удаляет volume БД и не подходит для перезапуска с сохранением данных.

Проверка БД из одноразового контейнера без запуска polling:

```powershell
docker compose --profile bot run --rm --no-deps bot python -m app.check_db
```

Сервис `bot` запускается через профиль `bot`; обычный запуск БД не запускает второй polling-процесс. Образ содержит код, зависимости и SQL-миграции. `.env`, конфиг и OAuth-файлы в образ не копируются. Используется Python 3.12.10, пользователь приложения — UID 10001, без root.

После изменения кода требуется сборка образа; одного `restart` недостаточно. Если после сохранения конфига через редактор контейнер продолжает видеть старую версию bind-файла, пересоздайте сервис командой с `--force-recreate`.

### Однократное истечение заявок

Обычно отдельный процесс не нужен: проверка уже встроена в бота. Для обслуживания при выключенном боте:

```powershell
.\.venv\Scripts\python.exe -m app.expiry_worker --once
```

Эта команда меняет статусы и формирует очередь уведомлений. Доставку выполняет работающий бот. Вызов без `--once` запускает самостоятельный цикл; при обычном запуске бота он не требуется.

### Поиск свободных окон через CLI

Команда доступна зарегистрированному пользователю. Замените `123456789` своим Telegram ID. Даты должны быть будущими, с часовым поясом; пример использует Сеул.

```powershell
.\.venv\Scripts\python.exe -m app.booking_cli --actor 123456789 windows --start "2026-11-10T00:00:00+09:00" --end "2026-11-13T00:00:00+09:00" --hours 5
```

Возвращаются занятые интервалы, физически свободные промежутки и допустимые начала аренды. Не каждый свободный промежуток подходит для бронирования: учитываются минимум часов, ожидание уборки и её окончание. Максимальный диапазон поиска — 31 день. Без `--hours` возвращаются диапазоны допустимой длительности. Поиск не создаёт удержание и не рассчитывает цену.

В коде доступна функция `app.availability.get_availability_windows(connection, actor, starts_at, ends_at, duration_hours=5)`. Действующий Telegram ID берётся из доверенного контекста обработчика.

CLI также поддерживает `list`, `available`, `create`, `submit`, `confirm`, `cancel`, `move`; параметры доступны через `--help`. Это доверенный инструмент с доступом к БД, а не публичный API аутентификации. Изменяющие команды создают реальные записи и уведомления. Для создания нужен UUID `--request-key`, для изменений — актуальная `--version`.

### Необязательный FastAPI

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

- `/health/live` — работает процесс API.
- `/health/ready` — API имеет доступ к БД; при ошибке возвращает HTTP 503.
- `/docs` — документация HTTP API.

Успешный ответ API не доказывает, что запущен Telegram polling или работает Google Calendar. Запуск FastAPI не запускает бота. Публичных HTTP-методов бронирования сейчас нет.

## Диагностика

| Симптом | Проверка и действие |
| --- | --- |
| `ConnectionTimeout`, PostgreSQL недоступен | Запустите Docker Desktop и `docker compose up -d --wait db`; проверьте `app.check_db`, порт и пароль |
| Windows не даёт занять порт | Проект использует `127.0.0.1:15432`; при его изменении согласуйте Compose и `.env` |
| Конфликт Telegram polling | Оставьте один процесс: Windows или контейнер с этим токеном |
| `Registered user required` | Отправьте `/start` этому боту и используйте свой числовой Telegram ID |
| Нет административного доступа | Проверьте роль и `active`; первого владельца назначает только локальный bootstrap |
| Нет созданной блокировки | Нажмите финальное «Да, выполнить», затем откройте список «Блокировки» |
| Нет события в Google | Проверьте `calendar.enabled`, ID, `app.google_calendar check` и статус Calendar в карточке; `pending` в Google не публикуется |
| Не найден `google_token.json` | Выполните `app.google_calendar auth` на Windows; скачанный OAuth JSON не заменяет токен |
| Google `403 access_denied` при входе в Testing | Добавьте аккаунт входа в Audience → Test users правильного проекта Google Cloud |
| После правок Google события возвращаются назад | Изменяйте бронь в боте: синхронизация односторонняя, из БД в Google |
| Другой пользователь не видит календарь | Проверьте Google email в доступе и выбранный аккаунт; добавьте календарь по приглашению либо по ID в браузере |
| Нет уведомления об уборке | Проверьте глобальный флаг, персональный флаг, роль, `active`, статус `confirmed` и назначенное время уборки; бот должен работать |
| Не удалось рассчитать праздничный тариф | Проверьте зависимости (`holidays`), поддерживаемый год и логи; обычные праздники KR рассчитываются автоматически, дополнительные даты задаются в `pricing.holiday_dates` |
| Нет свободных часов | Проверьте длительность, брони, блокировки, недельные окна и ожидание уборки; начните выбор даты заново |
| Устарела карточка или кнопка | Откройте запись через актуальный список; незавершённые черновики не переживают перезапуск |

## Тестирование

Быстрые тесты без БД:

```powershell
$env:RUN_DB_TESTS = '0'
.\.venv\Scripts\python.exe -m unittest discover -s tests
```

Полный набор с PostgreSQL:

```powershell
$env:RUN_DB_TESTS = '1'
.\.venv\Scripts\python.exe -m unittest discover -s tests
Remove-Item Env:RUN_DB_TESTS
```

Тесты создают изолированные схемы и удаляют либо откатывают тестовые данные. Пользователю БД нужны права на создание схем. Google API и Telegram-отправки имитируются; реальные сообщения и календарные события тесты не создают.

Для запуска полного набора в собранном Docker-образе:

```powershell
$aceTestsMount = (Join-Path (Get-Location) 'tests') + ':/tests:ro'
docker compose --profile bot run --rm --no-deps -e RUN_DB_TESTS=1 -v $aceTestsMount bot python -m unittest discover -s /tests
```

На момент обновления документации — 215 тестов; последний полный прогон в Docker занял около 20 секунд. После небольших изменений достаточно быстрых и затронутых тестов. Полный набор запускается при завершении функции; повтор в Docker нужен при изменении контейнера, зависимостей или проверке Linux-совместимости.

## Устройство проекта и ограничения

### Данные

| Таблица | Назначение |
| --- | --- |
| `clients` | Внутренний ID, уникальный Telegram ID, чат, профиль и язык |
| `admins` | Роль, доступ, уведомления и Google email; имя берётся из `clients` |
| `bookings` | Аренда или блокировка, статус, даты, суммы, уборка, версия и технические очереди |

Отдельных таблиц помещений, операций и уведомлений нет. В `bookings` хранятся JSONB-поля `request_data`, `admin_notifications`, `payment_receipt`, `calendar_sync`, `cancellation`, а также UUID создания `request_key`. `cancellation` содержит снимок условий, расчёт отмены клиентом и подтверждение возврата. Метаданные доставки не увеличивают бизнес-версию; бизнес-изменения увеличивают `version`.

Нотификации и синхронизация сохраняют состояние в БД и повторяют временно неудавшиеся операции. При потере сетевого ответа после фактической отправки повтор Telegram-сообщения возможен. Защита создания брони и записи предоплаты от дублей выполняется отдельно на сервере.

### Границы текущей версии

- Режим работы — long polling; домен и VPS для локального запуска не требуются.
- Google Calendar не является источником занятости и не синхронизируется обратно в БД.
- Оплату проверяет человек; OCR, банковский API и автоматическое подтверждение не подключены.
- В интерфейсе нет отдельной операции учёта остатка оплаты или возвратов; поле `balance_paid_amount` само по себе не означает наличие такого сценария.
- Нет отдельных пользовательских действий фактического входа/выхода и завершения уборки.
- Нет LLM, Mini App и проверки внешних площадок.
- Приложение не переключается на `TELEGRAM_PROD` автоматически.
- Текущий PostgreSQL-пользователь из Compose имеет административные права; разделение прав приложения и миграций пока не реализовано.
